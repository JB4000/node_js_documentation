Server-side rendering and client-side rendering

When we build a website, we need to decide where the HTML content should be constructed.

Two approaches are server-side rendering (SSR) and client-side rendering (CSR).

Server-side rendering (SSR)

With SSR, the server constructs the HTML before sending it to the browser.

The browser receives a page where the content is already included in the HTML. It can display that content without first having to use JavaScript to create it.

The server might read HTML files, combine components, or insert data into a page before sending the response.

SSR does not mean that the server must construct the HTML again for every request. We can also construct a page once and reuse it for several requests, if that matches the application.

Client-side rendering (CSR)

With CSR, JavaScript running in the browser constructs or updates the content of the page.

The server can send an initial HTML document that contains little content. JavaScript can then fetch data from an API and use it to create HTML elements and update the DOM.

This means the browser does more of the work.

CSR can be useful for applications where the user interacts with the page and only parts of the content need to change.

Performance and resource usage

SSR and CSR use resources differently.

With SSR, the server does the work of constructing the HTML. This can make the initial content appear sooner because the browser receives HTML that is already prepared.

But constructing HTML for many requests can also require more work from the server.

With CSR, the browser does more of the rendering work. It needs to download JavaScript code, execute it, and fetch data before the content is displayed.

This can delay the initial display of useful content. But after the application has loaded, JavaScript can update smaller parts of the page without loading a new HTML document.

The choice of apporach depends on the application, the amount of JavaScript, the server etc.

Search engine optimization (SEO)

Search engines need to understand the content of a website so they can index it.

With SSR, the content is already included in the HTML response. This makes it easier for search engines to check the content without having to execute JavaScript first.

With CSR, some content might only appear after JavaScript has been executed. Some search engines can execute JavaScript, but it can make indexing more complicated.

This is one reason SSR can be useful for websites where search engine visibility is important.

Combining SSR and CSR

We do not have to choose only one approach for an entire website.

A server can send HTML containing the initial content, while browser JavaScript handles later updates and interactions.

For example, a product page could be rendered on the server so the product information is available immediately. JavaScript could then update the selections or shopping cart without reloading the page.

The important difference is where the content is constructed and when the work happens.

Fetch and data from the server

The frontend can use fetch() to make HTTP requests to the server. fetch() returns a Promise so the browser can continue running other code while waiting for the response. 


            fetch('/api/animals')
                .then(response => response.json())
                .then(result => console.log(result.data));

The first .then() receives the HTTP Response object. response.json() reads and parses the JSON response body and also returns a Promise. The next .then() receives the parsed JavaScript value.

If the server sends an object like this: 


            res.send({
                data: animals
            });

then the frontend can access the animals through result.data.

Implicit and explicit return

An arrow function without curly braces implicitly returns the expression. This means that the Promise returned by response.json() is returned from the callback too. 


            .then(response => response.json())

If curly braces are used for the function body, return has to be written explicitly. 


            .then(response => {
                return response.json();
            })

Sending JSON with POST

fetch() can take a second argument containing options for the request. When we want to send a JavaScript object as JSON, we can specify the HTTP method, the content type and the request body. 


            const newAnimal = {
                name: 'Otter',
                age: 4
            };

            fetch('/api/animals', {
                method: 'POST',
                headers: {
                    'Content-Type': 'application/json'
                },
                body: JSON.stringify(newAnimal)
            })
                .then(response => response.json())
                .then(result => console.log(result.data));

The second argument to fetch() is still a JavaScript object. 'Content-Type' is written with quotes because the property name contains a hyphen.

JSON.stringify() converts the JavaScript object into JSON text before it is sent in the request body. On the server express.json() can parse the JSON and make the resulting JavaScript object available through req.body. 


            JavaScript object
                    ↓
            JSON.stringify()
                    ↓
            JSON in request body
                    ↓
            express.json()
                    ↓
            req.body

Semantic HTML

Semantic HTML means using HTML elements that describe the purpose of the content they contain. Instead of using a generic div for everything, we can use elements that tell us what different parts of the page are used for.

Some semantic elements we have used in the course are nav, main and footer. 


            <body>
                <nav>
                    <a href="/">Home</a>
                </nav>

                <main>
                    <h1>My website</h1>
                    <p>This is the main content.</p>
                </main>

                <footer>
                    <p>This is the footer.</p>
                </footer>
            </body>

The nav element contains navigation links. The main element contains the main unique content of the page. The footer element contains information at the bottom of the page.

We can also use section to group related content. A section will normally have a heading that describes what it contains. 


            <main>
                <section>
                    <h2>About the project</h2>
                    <p>Information about the project.</p>
                </section>

                <section>
                    <h2>Contact</h2>
                    <p>Contact information.</p>
                </section>
            </main>

Semantic HTML makes the structure of a page easier to understand. It also helps browsers, screen readers and other tools understand the purpose of different parts of the content.

CSS layout

CSS controls how HTML elements are displayed and positioned on a page. In the course we looked a bit at different ways of arranging elements, including block layout, Flexbox and Grid.

Block layout

Block elements normally start on a new line and take up the available width of their container.

Elements such as div, section and p are block elements by default. 


            .container {
                display: block;
            }

With block layout, elements are normally placed below each other. This is useful for typical page content such as paragraphs and sections.

Flexbox

Flexbox is used to arrange elements in one direction, either horizontally or vertically. 


            .container {
                display: flex;
                flex-direction: row;
                gap: 1rem;
            }

display: flex makes the container a flex container. Its direct children become flex items.

flex-direction: row arranges the items horizontally. Using column instead arranges them vertically. The gap property adds space between the items. 


            .container {
                display: flex;
                flex-direction: column;
            }

Flexbox is useful when we want to control how elements share space or align inside a container.

Grid

CSS Grid is used to arrange elements in rows and columns. This makes it useful when we want to control a layout in two directions. 


            .container {
                display: grid;
                grid-template-columns: 1fr 1fr;
                gap: 1rem;
            }

display: grid makes the container a grid container. grid-template-columns defines the columns. In this example, 1fr 1fr creates two columns that share the available space equally.

Block layout is useful for ordinary document flow. Flexbox is useful for arranging items in one direction, while Grid is useful for layouts with rows and columns.

CSS units

CSS uses different units to define sizes, spacing and positions. Some units use fixed values, while others depend on the font size, parent element or browser viewport.

px, rem and em

px is a CSS pixel. It is for when we want to specify a size directly.

rem is relative to the font size of the root html element. em is relative to the font size of the element itself when used for most properties, such as padding. For font-size, it is relative to the parent's font size. 


            .example {
                border-width: 2px;
                padding: 1rem;
                margin-bottom: 2em;
            }

If the root font size is 16px, then 1rem is 16px. If an element has a font size of 20px, then 2em for its margin is 40px.

Percentages

The % unit is relative to another size. For example, a width of 50% is normally half the width of the containing element. 


            .box {
                width: 50%;
            }

vh and vw

vh is relative to the viewport height, and vw is relative to the viewport width. The viewport is the visible area of the browser page.

100vh corresponds to the full viewport height, while 50vw corresponds to half the viewport width. 


            .container {
                min-height: 100vh;
                width: 50vw;
            }

Viewport units are useful when we want an element's size to depend on the browser window and not its content.

Positioning the footer with Flexbox

When a page does not have much content, the footer can end up higher on the page because the content does not fill the browser window.

In the course we used Flexbox to make the main content take up the remaining space, so the footer stays near the bottom of the page even when there is little content. 


            body {
                min-height: 95vh;
                display: flex;
                flex-direction: column;
            }

            main {
                flex: 1;
            }

min-height: 95vh gives the body a minimum height corresponding to 95% of the viewport height.

display: flex makes the body a flex container. flex-direction: column arranges its direct children vertically.

flex: 1 allows the main element to grow and take up the available space between the header and footer. This pushes the footer down when the page has little content.

Using calculated heights instead

Another approach is to calculate the height of the main content based on the space used by the other elements. 


            nav {
                height: 15vh;
            }

            main {
                min-height: calc(100vh - 26vh);
            }

            footer {
                height: 5vh;
            }

This approach depends on the heights of the other elements. If their sizes change, we might also need to update the calculation.

Flexbox is effective for this layout because the main element can take up the remaining space without manually calculating its height.

JavaScript in the browser

JavaScript can be used to change the content of an HTML page after it has been loaded in the browser.

Updating the footer year

In the course we used JavaScript to display the current year in the footer instead of writing a fixed year in HTML.

First, we can give an HTML element an id so JavaScript can find it. 


            <footer>
                <p id="footer-copyright"></p>
            </footer>

We can then use document.getElementById() to find the element and textContent to change its text. 


            const currentYear = new Date().getFullYear();

            document.getElementById('footer-copyright').textContent =
                `Copyright © ${currentYear}`;

new Date() creates a Date object, and getFullYear() returns the current year. The template literal inserts that year into the text.

This way, the footer year updates automatically without having to change the HTML every year.

Script placement and defer

JavaScript that works with HTML elements must run after those elements are available in the document.

One approach is to place the script at the end of the body, after the HTML elements it needs to access. 


            <body>
                <main>
                    <h1>My website</h1>
                </main>

                <footer>
                    <p id="footer-copyright"></p>
                </footer>

                <script src="/scripts/footer.js"></script>
            </body>

We can also load an external JavaScript file using defer in the head. 


            <head>
                <script src="/scripts/footer.js" defer></script>
            </head>

With defer, the browser can download the script while parsing the HTML, but waits until the document has been parsed before executing it.

This means the JavaScript can access the footer element even though the script tag is placed in the head.

Server-Side Rendering (SSR)

Server-side rendering means that HTML is constructed on the server and sent to the browser as a complete page.

For this documentation site, Node.js reads reusable HTML components and combines them with documentation content using a custom templating engine. The completed pages are constructed when the server starts.

Express then sends the preconstructed HTML when a user visits a route. 

app.get("/frontend", (req, res) => {
    res.send(frontendHtml);
});

This separates page construction from HTTP request handling. It also avoids rebuilding the same HTML for every request.

Reading and Reusing HTML Components

A templating engine can reuse HTML from separate files. In this project, Node.js reads the HTML components using fs.readFileSync(). 

export function readComponent(componentName) {
    const filePath = path.join("public", "components", `${componentName}.html`);
    return fs.readFileSync(filePath, "utf8");
}

path.join() creates the file path, and fs.readFileSync() reads the file as a string. The templating engine can then use replace() to insert the component into the layout. 

const header = readComponent("header");
layout = layout.replace("{{header}}", header);

Templating Engine Structure

The templating engine is split into different JavaScript files. Each file has its own responsibility, so the code is easier to read and to change. 

templatingEngine/
    pages.js
    navigation.js
    templatingEngine.js
    renderedPages.js

public/
    components/
        head.html
        header.html
        sidebar.html
        footer.html
        layout.html

pages.js contains information about the documentation pages, including their routes and file paths.

navigation.js reads the documentation headings from the html and creates the links for the sidebar.

templatingEngine.js reads the HTML components and combines them with the documentation content.

renderedPages.js constructs all the documentation pages when the server starts. The completed HTML is then imported into app.js and sent through the Express routes.

Generating the Sidebar Navigation

The sidebar navigation is generated automatically from the documentation pages. This is handled in navigation.js.

The readHeadings() function reads the HTML file and finds the article content. It then looks for h2 headings and extracts their text and id attributes.

The headings are stored in an array of objects containing an id and text. This information is used by createSectionLinks() to create the links for each heading.

The createSubjectGroups() function goes through the pages defined in pages.js. It creates an expandable details element for each subject and adds its section links.

For links on the current page, only the heading id is used. For links to another page, the route is included in the URL. This makes it possible to navigation between subjects(pages) and sections.

The generated navigation is inserted into sidebar.html by the templating engine.
