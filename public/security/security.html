Security

Data received from a user should not automatically be considered safe. This matters both when the server receives data and when the frontend later displays data in the browser.

Two of the security considerations we have looked at in the course is Cross-Site Scripting (XXS) and Cross-Origin Resource Sharing (CORS)

Cross-Origin Resource Sharing (CORS)

CORS stands for Cross-Origin Resource Sharing.

Browsers have security rules that restrict how JavaScript on one website can access data from another origin.

An origin is defined by the protocol, hostname and port. For example, http://localhost:8080 and http://localhost:3000 are different origins because they use different ports.

CORS and external APIs

When JavaScript in the browser uses fetch() to request data from an external API, the browser might block access to the response because of CORS.

The external API must allow the origin of our website to read the response.

This can be a problem when we want to use an API that does not allow requests from our frontend.

Calling an API from the server

We can avoid this browser CORS problem by making the external API request from our Node.js server instead.

The browser sends a request to our own Express server. Express then requests the data from the external API and sends the result back to the browser.

Node.js is not restricted by the browser's CORS rules when making server-side requests.

This works because the browser only needs to communicate with our own server, using the same origin.

CORS is a browser restriction

CORS is enforced by the browser.

A request from frontend JavaScript and a request from Node.js do not have the same CORS restrictions.

This is one reason we might choose to fetch external data on the server instead of directly from the frontend.

Cross-Site Scripting - XSS

Cross-Site Scripting is when attacker-controlled content causes code to be executed in another user's browser when using a website.

An example of problematic user input could be: 


            <img src="invalid" onerror="alert('XSS')">

The value by itself is just data. Storing the string in a database or having it in the Node.js application does not make the JavaScript execute. The dangerous situation happens if a browser later interprets the data as HTML.

textContent and innerHTML

How we place user input data into the page makes a difference.

If the data should be displayed as text, we can use textContent. 


            description.textContent = data.description;

If data.description contains: 


            <img src="invalid" onerror="alert('XSS')">

the browser displays those characters as text. It does not create an <img> element, so the onerror handler is not executed.

Using innerHTML is different: 


            description.innerHTML = data.description;

innerHTML tells the browser to interpret the string as HTML. In this example the browser creates an image element. The source "invalid" cannot be loaded, so the onerror code can execute.

Rule for the course: avoid innerHTML for user input data when the data should only be displayed as text. Use textContent instead.

Where XSS code executes

The injected frontend code is interpreted and executed by the client's browser.

For example, receiving and storing this string does not make the Node.js process execute the JavaScript inside it: 


            <img src="invalid" onerror="alert('XSS')">

It becomes dangerous when the value reaches the browser and it treats it as HTML and executes the code.

Validation and sanitization

Validation and sanitization are different. Validating input means checking whether the input follows the rules for the data.

For example, we could require an animal name to be a string between 1 and 50 characters. 


            name must be a string
            name must contain between 1 and 50 characters

Sanitization is removing dangerous content in data that is validated.

Input can pass validation and still contain dangerous content. Checking that a text has an allowed length does not make everything inside the text safe.

A simple sanitization example

In class we also made a simple sanitization function by replacing characters that have a special meaning in HTML with their HTML entities. 


        function sanitizeXSS(string) {
            return string
                .replaceAll('&', '&amp;')
                .replaceAll('<', '&lt;')
                .replaceAll('>', '&gt;')
                .replaceAll('"', '&quot;')
                .replaceAll("'", '&#39;')
                .replaceAll('`', '&#x60;')
                .replaceAll('/', '&#x2F;');
        }

For example, the function can be used before putting a string into innerHTML. 


        divContainer.innerHTML = sanitizeXSS(
            `<img src="x" onerror="alert('XSS')">`
        );

The function first replaces & and then replaces characters such as <, > and quotes with their HTML entity representations. The browser will then not interpret the string as the original HTML element.

When the content is only supposed to be text, using textContent is still simpler because we do not need to interpret the value as HTML at all.

Protection in the frontend and backend

The course looks at protection on both sides. In the frontend we should avoid putting user-controlled data into innerHTML when it should be text. On the backend we should sanitize data that can contain dangerous content.

It is useful to protect both sides even if our own frontend currently uses textContent correctly.

A REST API can have more than one client. We cannot know that every project using data from the API will always display it safely. Another client could take a string returned by the API and put it directly into innerHTML.

This is one reason not to think of the frontend as the only place where dangerous data is a problem.
