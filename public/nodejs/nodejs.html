Node.js & Tools

Node.js is a JavaScript runtime that makes it possible to run JavaScript outside of the browser. In this course we use Node.js to run JavaScript on the server.

A JavaScript file can be run with Node.js from the terminal by writing node followed by the name of the file. 


            node app.js

Synchronous and asynchronous file operations

Node.js can read and write files using the built-in fs (file system) module.

File operations can be synchronous or asynchronous. The important difference is whether JavaScript must wait for the operation to finish before continuing.

Synchronous file operations

A synchronous operation blocks the single JavaScript thread until the operation is finished.

For example, readFileSync() reads a file and returns its contents. JavaScript cannot continue to the next statement until the file has been completely read. 

import fs from "fs";

const content = fs.readFileSync("./page.html", "utf8");

console.log(content);

This code is easy to read because the result is available immediately after the function returns.

However, if reading the file takes time, the single JavaScript thread is blocked.

In an Express application, this can be a problem because the server will have to handle requests from many users.

Asynchronous file operations

An asynchronous file operation allows JavaScript to continue while the file operation is being handled.

For example, we can use .readFile() together with await: 

import fs from "fs";

const content = await fs.readFile("./page.html", "utf8");

console.log(content);

The await keyword pauses the current async function until the returned promise is resolved, but it does not block the Node.js event loop like an synchronous file operation does.

This allows Node.js and JavaScript to work on other tasks while waiting for the file operation to finish.

Choosing between asynchronous and synchronous

Imagine that our Express server needs to read an HTML file whenever a user requests a page.

If we use readFileSync() inside the route, the JavaScript thread is blocked until the file has been read. Other requests will have to wait.

If we use an asynchronous file operation, Node.js can handle other requests and code while the file is being read.

That makes asynchronous a preference for file access when handling requests.

When synchronous operations are useful

Synchronous operations can be a good choice.

For example, an application might read its HTML templates once when the server starts and reuse the results for later requests.

In that situation, using readFileSync() makes the startup code simple, and the file-reading operation does not need to happen for every request.

The choice depends on when the file is read and if blocking prevents the server from handling other urgent work.

Speed

Asynchronous file operations do not necessarily make an individual file read faster.

The purpose is to make Node.js able to use the waiting time to handle other work instead of blocking the JavaScript thread.

This can make a server better at handling many requests in a more balanced way.

NPM and packages

NPM is the package manager we use with Node.js. It can be used to install packages that we want to use as dependencies in a project. Express is an example of a package that we use in the course.

Other languages and environments have similar tools. In class NPM was for example compared with Maven. They solve some of the same problems even though the files and commands used by the tools are different. For example, Mavens lifecycle sequence is different from the selective call to scripts in Node.js.

package.json

package.json contains information about a Node.js project. One important purpose is to declare which packages the project depends on. 


                {
                    "dependencies": {
                        "express": "5.2.1"
                    }
                }

In this example Express is a dependency of the project. The dependency declaration makes it possible to know which package and version the project expects without having to include the installed package itself in the repository.

package.json can also contain metadata about the project and scripts that can be run with NPM.

NPM scripts

We can define scripts in package.json to make it easier to run commands for a Node.js project. Instead of writing the full command in the terminal every time, we can give it a name.

In the course we used different scripts for starting the server normally and for starting it during development. 


                {
                    "scripts": {
                        "start": "node app.js",
                        "start-dev": "nodemon app.js"
                    }
                }

The scripts are defined inside the scripts object in package.json. The property name is the name of the script, and the value is the terminal command that NPM runs.

We can run the scripts from the terminal: 


            npm start
            npm run start-dev

npm start runs the start script. For a custom script such as start-dev, we use npm run followed by the script name.

The first script starts the application with Node.js. The second starts it with Nodemon, which restarts the server when we change the source code.

Scripts make it easier to run the project because we can use the same commands without having to remember the full command behind each script.

Environment variables and cross-env

Environment variables are values that a program can read from the environment where it is running. In Node.js we can access them through process.env.

In the course we used an environment variable to decide which port the Express server should listen on. 


            const PORT = process.env.PORT ?? 8080;

            app.listen(PORT);

process.env.PORT reads the environment variable named PORT. The ?? operator gives a fallback value when the variable is null or undefined.

This means the server uses port 8080 when no PORT environment variable has been provided. If we provide a different port, the same application can listen on that port without changing the source code.

Setting an environment variable

In the terminal we can set an environment variable for a single command: 


            PORT=9090 node app.js

This starts the application with process.env.PORT set to 9090 for that command.

The syntax for setting environment variables is not the same in every terminal or operating system. It is impractical to use different commannds or make different scripts for different operating systems. We can use cross-env to solve that problem with scripts.

Using cross-env in NPM scripts

cross-env is a package that lets us set environment variables when running commands through NPM scripts without depending on the operating system.

In class we have used scripts like these: 


                {
                    "scripts": {
                        "start": "cross-env PORT=80 node app.js",
                        "start-dev": "cross-env PORT=9090 nodemon app.js"
                    }
                }

The start script starts the server with Node.js on port 80. The start-dev script starts it with Nodemon on port 9090.

We can run them with: 


            npm start
            npm run start-dev

When we run one of these scripts, cross-env sets the PORT environment variable before starting the Node.js process.

The application then reads the value through process.env.PORT.

Nullish coalescing and logical OR

We can use both ?? and || to provide fallback values, but they do not work the same way. 


            const port1 = process.env.PORT ?? 8080;
            const port2 = process.env.PORT || 8080;

?? uses the fallback only when the value is null or undefined.

|| uses the fallback when the value is falsy, for example 0, false or an empty string.

Environment variables are read as strings, so the value "0" is not the same as the number 0.

Dependencies and devDependencies

Packages in a Node.js project can be declared as dependencies or devDependencies in package.json.

Dependencies are packages that the application needs when it runs. Express is an example because our server uses Express to handle HTTP requests.

devDependencies are packages that we use during development, but that are not needed to run the application in production.

Nodemon is an example of a development tool because it restarts the server when we change the code. 


            {
                "dependencies": {
                    "express": "5.2.1"
                },
                "devDependencies": {
                    "cross-env": "^10.1.0",
                    "nodemon": "^3.1.10"
                }
            }

This is an example of how the two types of dependencies can be organized in package.json. The exact versions depend on the packages installed in the project.

We can install a normal dependency with: 


            npm install express

To install a package as a devDependency, we can use the -D flag: 


            npm install -D nodemon

The -D flag is short for --save-dev. NPM then adds the package to the devDependencies section of package.json.

A package installed as a devDependency can still be used in any script.

Working with NPM from the terminal

There are different ways of setting up a Node.js project with NPM. We have practiced both creating package.json ourselves and letting NPM create it.

If package.json has already been created and contains the dependencies for the project, we can install those dependencies with: 


        npm install

NPM reads package.json and installs the dependencies into node_modules. This is also why we do not need to get node_modules from Git when cloning an existing project. The dependencies will be installed again with NPM.

Instead of writing package.json by hand, NPM can initialize a project for us. 


        npm init

This starts an interactive setup where NPM asks for information about the project before creating package.json.

The setup can also be made without going through the questions: 


        npm init -y

The -y flag accepts the default values, so package.json is created immediately. The file can still be changed afterwards.

Installing a package

We can install a specific package by giving its name to npm install. To install Express we can write: 


            npm install express

This installs Express into node_modules and adds Express as a dependency of the project in package.json

That is the difference between the two commands: npm install installs the dependencies already declared by the project, while npm install express asks NPM to add and install Express as a dependency.

Inspecting installed packages

NPM also has commands for checking which packages are installed in a project.

We can use npm ls to list the installed packages and their dependencies. 


            npm ls

The output shows the dependency tree for the project. Packages can have their own dependencies, so the tree may contain more packages than the ones we installed directly.

We can use the flag --depth=0 when we only want to see the top-level packages. 


            npm ls --depth=0

If we want to check a specific package, we can provide its name. 


            npm ls cross-env

This shows if cross-env is present in the projects dependency tree.

We can also inspect packages that have been installed globally on the computer. 


            npm ls -g
            npm ls -g --depth=0

The -g flag means global. A global installation is not tied to one specific project's node_modules directory.

Declaring the packages needed by the project in package.json makes it easy for someone else to install the dependencies and run the project.

node_modules

When packages are installed they are placed in the node_modules directory. This directory can contain a very large amount of files because the packages we install can have their own dependencies.

Rule for the course: do not push node_modules to the repository. The dependencies are declared by the project and can be installed again instead of storing all the installed package files in Git.

Nodemon

When running a Node.js server normally, changes to the source code will not automatically restart the running server. During development that would mean manually stopping and starting the server every time we make a change.

Nodemon is a development tool that watches the project files and restarts the Node.js process when the code changes. This makes development practical because the changed server code is automatically loaded.

Nodemon is a development tool. In production we do not want changes to source files to unexpectedly restart the application.

Running Nodemon

We can install Nodemon as a development dependency using NPM. 


            npm install -D nodemon

After installing Nodemon locally, we can run it through an NPM script in package.json. 


            {
                "scripts": {
                    "start-dev": "nodemon app.js"
                }
            }

We can then start the server with: 


            npm run start-dev

Nodemon starts the application and watches for changes to the source code files. When we save a change, Nodemon restarts the Node.js process automatically.

This is useful when working with Express because we can change a route, save the file, and test the updated server without manually restarting it.

If we only change a static HTML or CSS file, we normally just need to refresh the browser. Express can serve the updated files of this type without restarting the server.

In class we combined Nodemon with cross-env to set the server port: 


            {
                "scripts": {
                    "start-dev": "cross-env PORT=9090 nodemon app.js"
                }
            }

This script starts the application with Nodemon and sets the PORT environment variable to 9090. The application must read process.env.PORT for that setting to control the listening port.

Configuring Nodemon

Nodemon automatically restarts our Node.js application when files change. We can configure which file types it should watch.

By default, Nodemon watches code file types such as JavaScript.

We can create a nodemon.json file in the root of our project to configure which file extensions it watches.

For example:

{
    "ext": "js,mjs,cjs,json,css,html"
}

With this configuration, Nodemon also restarts the server when we change for example CSS or HTML files.

This can be useful when our application reads HTML files and constructs pages when the server starts. Restarting the server allows it to read the updated files.

Nodemon and browser refreshing

Nodemon restarts the Node.js server, but it does not automatically refresh the browser page.

If we change a CSS file that Express serves statically, we can normally just refresh the browser to see the change. The server does not need to restart.

However, if our server reads an HTML file only once during startup and stores the result, it must read the file again before the changes appear. Restarting the server is one way to do that.

So we should configure Nodemon based on how our application works.
