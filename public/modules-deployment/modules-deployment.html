Modules, Static Files & Deployment

Code organization with modules

As an application grows, keeping all our code in one file makes it harder to understand and maintain. We can use modules to split our code into smaller files with their own responsibilities. In this section we will use ES Modules and not CommonJS.

In JavaScript, we can use export to make functionality available to other modules and import to use it.

Import and export

For example, we can define a function in math.js:

export function add(a, b) {
    return a + b;
}

We can then import and use it in app.js:

import { add } from "./math.js";

console.log(add(2, 3));

This allows us to reuse functionality without putting all the code in the same file.

Single responsibility

The single responsibility principle means that a module should have one clear responsibility.

This does not mean that every function needs its own file. A module can contain several related functions that work together to handle the same responsibility.

For example, a module responsible for calculations could contain functions for addition, subtraction and multiplication.

Separation of concerns

Separation of concerns means organizing different parts of an application so that they handle different tasks.

For example, code that handles HTTP requests should not necessarily be responsible for every detail of how HTML is constructed.

Keeping these concerns separate makes the code easier to understand, change and test.

Encapsulation and abstraction

Encapsulation means keeping related functionality and its internal details together.

A module can export the functions other files need while keeping helper functions invisible.

Abstraction means hiding unnecessary details behind a simpler interface.

For example, another module might call a function named calculateTotal() without needing to know every step of the calculation.

Some differences:

  • Encapsulation is keeping related code and internal details together.
  • Abstraction is about exposing what other code needs without it having to understand how it works internally.

Module dependencies

When one module imports another, it depends on that module. For example, in the Planter project from class, the modules are connected like this: 

app.js
  ├──→ templatingEngine/pages.js
  │          └──→ templatingEngine/templatingEngine.js
  └──→ util/fetchPlants.js

The arrows show which modules import other modules.

app.js imports prepared pages from pages.js and functions for fetching plant data from fetchPlants.js.

pages.js imports constructPage() and readPage() from templatingEngine.js.

This means app.js can use the prepared pages without needing to know how the templating functions work internally. Each module has a different responsibility, and the imports show how they depend on each other.

When should we create a new module?

We could consider creating a new module when:

  • A file starts handling several different responsibilities.
  • We want to reuse functionality in multiple places.
  • Several functions belong together and form a clear responsibility.
  • A file becomes difficult to navigate or understand.
  • We want to have to change code at only one place instead of multiple places.

The point is not to create as many files as possible. It is to organize the code in a way that makes the application easier to understand and change.

Using modules in Express

In an Express application, we can use modules to separate route handling, reusable functionality and page construction.

Serving static files

The browser needs access to files like HTML, CSS, images and client side JavaScript to render and run a page. These files can be served as static files with middleware in Express. 

app.use(express.static('public'));

This statement tells Express to serve static files from the public folder. The browser can then request files from this folder directly without us manually creating a route for every file.

The path used by the browser is not the same as the physical path in the project. The public folder becomes a virtual root for the static files. 

public/
    frontpage/
        index.html
        frontpage.css
        frontpage.js

A CSS file that is located at public/frontpage/frontpage.css can therefore be requested from the browser with: 

<link rel="stylesheet" href="/frontpage/frontpage.css">

The browser does not use /public/frontpage/frontpage.css because public is already the root of the files that the middleware is serving.

Limiting access to files

We do not want the browser to have access to any random file in the project. A useful safety default is to deny access by default and explicitly allow what is needed.

The browser needs HTML, CSS, images and client side JavaScript, so there is a reason to make these files available. Server files like app.js, package.json have no reason to be available to the browser.

This is not decided by the file extension itself. A JavaScript file can be a client side file that should be served to the browser, while another JavaScript file can contain server code that should not be available. What matters is which files we have explicitly made available.

CDN versus local resources

When we use external libraries like Pico CSS or Highlight.js, we need to decide where the browser should load their files from.

We can use a CDN or serve the files locally from our own application.

Content Delivery Network (CDN)

CDN stands for Content Delivery Network.

A CDN is a network of servers that can deliver files such as CSS, JavaScript and images to users.

The servers can be located in different geographical areas. This means the browser might be able to download a file from a server that is closer to the user.

Using a CDN can also reduce the amount of traffic our own server needs to handle.

But we depend on the external CDN being available. If the CDN has problems, the browser might not be able to load the files.

Serving resources locally

Instead of using a CDN, we can install a library with npm and serve its files from our own Express application.

We can use express.static() to make the required files available to the browser.

This gives us more control over which version of the library we use, and we do not depend on an external CDN to deliver it.

But our own server must handle the requests for these files.

Example from this website

This documentation website uses Pico CSS for styling and Highlight.js for syntax highlighting in code examples.

Both libraries are installed through npm and served locally by Express instead of being loaded from a CDN.

This means the browser requests the library files from our Express application, just like it requests our own CSS and JavaScript files.

We can manage the library versions through our project's npm dependencies and do not need an external CDN to deliver them.

Which approach to use?

It depends.

A CDN can be useful because it distributes files across different servers and can improve loading performance.

Serving files locally can be useful when we want more control over the resources our application depends on.

We should consider performance, reliability and control when choosing between the two.

Root-relative and relative URLs

When we reference a CSS file, JavaScript file or another page in HTML, we can use different types of URLs.

A root-relative URL starts with /. This means the path starts from the root of the website, regardless of which page the browser is currently on.

In our documentation project we use: 


            <link rel="stylesheet" href="/styles/main.css">

Express serves this file from public/styles/main.css because we have configured public as the static root.

The same URL works from different pages, for example /frontend, /express and /nodejs.

Relative URLs

A relative URL does not start with /. The browser resolves it relative to the current document URL. 


            <link rel="stylesheet" href="styles/main.css">

If the current page is /frontend, the browser resolves this example to /styles/main.css.

But if the current page is /frontend/frontend.html, the browser resolves it to /frontend/styles/main.css.

This means the same relative URL can point to different locations depending on the page URL.

Shared assets

Our documentation website has several pages that use the same stylesheet.

Instead of having a separate copy of the stylesheet in every folder, we can keep one shared file inside public/styles.

Each HTML page can reference that stylesheet using the same root-relative URL: 


            <link rel="stylesheet" href="/styles/main.css">

This makes the paths consistent across the website. It also means that when we update the shared CSS file, the changes can affect all the pages that use it.

JavaScript modules

As a project grows it makes sense to split the code into different files. This creates the question of how code in one file can use functions and variables from another file.

We also do not necessarily want everything in a file to be accessible from other files. Some functions and variables might only be used internally in that file, while others are meant to be used by the rest of the application.

Modules give us a way to control this. A module can export the values that should be available to other modules. Another module can then import the values that it needs.

Named exports

We can export specific functions and variables by name: 

const animals = ['Cat', 'Dog'];

function getAnimals() {
    return animals;
}

function calculateSecretId() {
    return 42;
}

export {
    animals,
    getAnimals
};

In this example animals and getAnimals are exported. They are now available for other modules to import. calculateSecretId is not exported and is therefore only available internally in this module.

An importing module does not have to import everything that has been exported. It can choose only the values that it needs: 

import { getAnimals } from './animalService.js';

getAnimals();

getAnimals is a named export, so the name is written inside curly braces in the import. After it has been imported it can be used directly in this file.

Even though animals was also exported, it was not imported here. It is available to import, but it is not available by name in this file unless we import it.

Exporting when declaring a value

The export keyword can also be written directly where a function or variable is declared: 

export const animals = ['Cat', 'Dog'];

export function getAnimals() {
    return animals;
}

This has the same purpose as declaring the values first and listing them in an export afterwards. Both examples create named exports.

Default exports

A module can also have a default export. A default export is one value that is chosen as the default value to export from the module.

For example, we can put several functions in an object and export that object as the default: 

function getAnimals() {
    return ['Cat', 'Dog'];
}

function createAnimal(name) {
    return { name };
}

export default {
    getAnimals,
    createAnimal
};

The curly braces in this example create an object. The object has the properties getAnimals and createAnimal, and the complete object is the one value that is exported as default.

There are no parentheses after the function names in the object, so the functions are not called here. References to the functions are stored as values in the object.

A default export is imported without curly braces: 

import animalService from './animalService.js';

animalService.getAnimals();
animalService.createAnimal('Otter');

The name animalService is chosen in the importing file. Because this is a default import, it does not have to match a name from the exporting file. We could for example have called it service instead.

The imported value is an object, so its functions are accessed as properties with dot notation. animalService.getAnimals is a reference to the function and animalService.getAnimals() calls the function.

Named exports and default exports

Named exports and a default exported object can look quite similar, but the curly braces do not mean the same thing: 

export {
    getAnimals,
    createAnimal
};

Here the curly braces are part of the syntax for named exports. Two values are exported by name. They can be imported like this: 

import { getAnimals, createAnimal } from './animalService.js';

getAnimals();

In the following example the curly braces instead create an object: 

export default {
    getAnimals,
    createAnimal
};

There is now one default export, which is the object. If we import the object as animalService, the functions are properties on that object: 

import animalService from './animalService.js';

animalService.getAnimals();

ES Modules in the browser

If we want to use ES Modules in JavaScript that is run by the browser, the browser has to know that the JavaScript file is a module. This can be specified with type="module" on the script tag: 

<script type="module" src="/fruits/fruits.js"></script>

The JavaScript file can then use ES Module syntax to import from another JavaScript file: 

import farm from './fruitOrchard.js';

console.log(farm.fruitProcessingPlant());

In this example farm receives the default export from fruitOrchard.js. The name farm is chosen in the importing file because this is a default import.

type="module" is needed here because it is the browser that loads and runs fruits.js. A setting in Node's package.json does not tell the browser how it should interpret this file.

Modules in Node.js

We first used CommonJS as the module system in Node.js. For example, Express was imported with require(): 

const express = require('express');

CommonJS uses require() to import a value from another module and module.exports to define what a module exports. 

function add(a, b) {
    return a + b;
}

function subtract(a, b) {
    return a - b;
}

module.exports = {
    add,
    subtract
};

module.exports is assigned an object in this example. If another file requires the module, the returned value is therefore this object: 

const calculator = require('./calculator.js');

calculator.subtract(10, 3);

The name calculator is chosen in the file that imports the module. It is a variable that contains a reference to the object that was exported.

ES Modules in Node.js

We will use ES Modules instead of CommonJS going forward. Node.js has to know that our .js files should be considered ES Modules. This can be specified in package.json: 

{
    "type": "module"
}

We can then use the same import and export syntax that we use with ES Modules in the browser. Express can for example be imported like this: 

import express from 'express';

Our own files can also be imported as ES Modules: 

import animalService from './util/animalService.js';

There is a difference between these two paths. express refers to an installed package, while ./util/animalService.js is a relative path to one of our own files. ./ means that the path starts relative to the file where the import is written.

CommonJS and ES Modules

The two module systems therefore use different syntax for the same general problem: 

// CommonJS
const calculator = require('./calculator.js');

module.exports = {
    add,
    subtract
};

// ES Modules
import { add, subtract } from './calculator.js';

export {
    add,
    subtract
};

One advantage of using ES Modules is that we can use the same module system in both the browser and Node.js. We do not have to use ES Modules in frontend JavaScript and then switch to CommonJS when working with JavaScript on the server.

Fetching in Node.js

We have previously used fetch() in the browser to make an HTTP request to our Node.js server. Node.js can also use fetch() to make an HTTP request to another server.

This means that Node.js can have different roles in different HTTP communications. When the browser sends a request to our Node.js server, the browser is the client and Node.js is the server: 

Browser  -- HTTP request -->  Node.js
client                       server

If Node.js then uses fetch() to make a request to Google, Node.js is now the client in that communication: 

Node.js  -- HTTP request -->  Google
client                       server

Client and server are therefore roles in a communication. Node.js can act as a server when it receives a request from the browser and as a client when it makes a request to another server.

Using Node.js as a proxy

We can combine the two communications. The browser can make a request to our Express server, and code in the endpoint can make another HTTP request to an external server. 

app.get('/proxy', (req, res) => {
    fetch('https://www.google.com/')
        .then(response => response.text())
        .then(result => res.send(result));
});

First the browser makes an HTTP request to /proxy. Express receives the request and matches it to the route. The callback for the route then calls fetch(), which makes a new HTTP request to Google.

fetch() returns a Promise. Node.js does not have to stop doing other work while it waits for the response. When the response arrives, the first .then() receives the response.

The body of the response from Google contains HTML, so response.text() is used to read the body as text. response.text() is also asynchronous and returns a Promise.

When the text is available, the next .then() receives it as result. res.send(result) then sends it in the HTTP response from our Express server back to the browser. 

Browser
   |
   | GET /proxy
   v
Node.js / Express
   |
   | fetch('https://www.google.com/')
   v
Google
   |
   | HTML response
   v
Node.js / Express
   |
   | res.send(result)
   v
Browser

The browser has not made the request to Google in this example. It made a request to our Node.js server. It is the Node.js server that then becomes a client and makes the request to Google.

package.json and npm

A Node.js project can have a package.json file containing information and configuration about the project. It can for example contain metadata about the project and information about its dependencies.

A package.json can be created with npm init. We can also use: 

npm init -y

The -y option accepts the default values instead of asking questions about the project one at a time.

Project metadata

Some properties describe the project itself: 

{
    "name": "planter",
    "version": "0.0.1",
    "description": "A website for keeping track of plants care",
    "license": "MIT",
    "author": "Mr Code"
}

name is the name of the project and version is the version of the project. Other properties can contain information such as a description, license and author.

Dependencies

Packages that the project depends on can be listed under dependencies: 

{
    "dependencies": {
        "express": "^5.2.1"
    }
}

In this example Express is a dependency of the project. The version number also tells npm which versions can be installed.

If the version is written without a symbol: 

"express": "5.2.1"

the dependency is pinned to that exact version. With the caret: 

"express": "^5.2.1"

compatible newer minor and patch versions can be installed, while the major version stays at version 5.

Installing dependencies

Express can be installed with: 

npm install express

If the dependencies are already described in package.json, they can be installed with: 

npm install

Writing a dependency in package.json describes that the project needs the dependency. It does not by itself download the package. npm install performs the installation.

ES Module configuration

package.json can also contain configuration that changes how Node.js treats the JavaScript files in the project: 

{
    "type": "module"
}

As described earlier, this tells Node.js that the .js files in the package should be considered ES Modules.

Serverless and in-memory data

During development we can store data in a variable on the server: 

const animals = [
    { id: 1, name: 'Cat' }
];

app.post('/api/animals', (req, res) => {
    animals.push(req.body);

    res.send({
        data: req.body
    });
});

When the local Node.js server keeps running, the same process stays in memory. If the animals array is mutated, later requests to that running process can therefore see the changed array.

If the process is restarted, the variables are created again from the code and the changes to the array are lost.

Serverless deployment

With serverless deployment the application does not have a server process running all the time. A server instance can instead be started when it is needed to handle a request and shut down again afterwards.

Because of this we cannot expect variables on the server to persist between requests. A later request can be handled without the state that was created by an earlier request.

An in-memory array is therefore useful while learning how CRUD and REST endpoints work, but it should not be treated as persistent storage in serverless deployment.
